# 审查历史存储方案说明

## 现状

当前项目的审查历史默认落到本地 SQLite 数据库：

- 路径：`data/review-history.db`
- 实现：`ReviewHistoryRepository` / `ReviewHistoryMapper` / `ReviewHistoryStatisticsService` / `ReviewHistoryMigrator`

如果还没有实际启动过应用，这个文件和 `data/` 目录可能还不会出现。应用启动时会自动建表。

---

## 当前方案：本地 SQLite 数据库

### 优点

- 不依赖额外数据库服务
- 支持分页、筛选、排序和统计
- 比 JSONL 更适合长期查询
- 适合当前阶段从 Demo 走向本地工具化

### 缺点

- 不适合多实例同时写入
- 不适合高并发团队级部署
- 数据库文件仍然依赖本地磁盘
- 后续平台化时仍建议迁移到 MySQL 或 PostgreSQL

### 适用场景

- 个人项目
- 学习项目
- 小规模内部工具

---

## 旧 JSONL 兼容

旧文件路径仍然保留为迁移来源：

- `data/review-history.jsonl`

如果 SQLite 数据库为空，应用启动时会尝试把旧 JSONL 数据导入 SQLite。迁移逻辑由 `ReviewHistoryMigrator` 负责，`ReviewHistoryService` 只保留对外编排。

---

## 数据库方案

可以迁移到 MySQL、PostgreSQL 或 MariaDB。

### 优点

- 支持索引和分页
- 支持复杂筛选和聚合
- 适合长期保存和团队使用
- 容易做报表和趋势分析

### 缺点

- 需要额外部署和维护
- 需要设计表结构
- 改造量比文件方案大

### 适用场景

- 团队化使用
- 长期运行
- 需要报表和统计

---

## 独立日志存储方案

可以接入 ELK、OpenSearch、Loki、ClickHouse 等。

### 优点

- 很适合留痕和审计
- 适合按时间检索
- 适合排障和运维分析

### 缺点

- 不一定适合业务级关系查询
- 落地成本更高
- 不如数据库直观

### 适用场景

- 强审计场景
- 运维分析场景
- 长期留痕场景

---

## 专门的审查历史服务

当项目进一步平台化时，可以把历史模块拆成独立服务。

### 优点

- 职责更清晰
- 易于扩展
- 便于统一治理和统计

### 缺点

- 架构复杂度更高
- 需要服务间通信
- 维护成本更高

### 适用场景

- 平台化审查系统
- 多来源审查接入
- 更大规模团队协作

---

## 推荐升级路线

1. 短期使用 SQLite 作为主存储
2. 中期根据使用量评估 MySQL 或 PostgreSQL
3. 后期按需引入独立日志或独立历史服务

### 最稳的迁移顺序

1. 保留 JSONL 作为一次性迁移来源
2. 新增 SQLite 表结构和索引
3. 让写入和查询都走 SQLite
4. 后续如需平台化，再迁移到 MySQL 或 PostgreSQL
5. 保留 `sourceUrl`、`commitSha`、`diffHash` 等轻量引用字段
