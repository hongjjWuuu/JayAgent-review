# 项目结构速读版

> 这份文档按包名梳理 `src/main/java/com/jayagent/jayagent_review` 下每个类的职责，并补上主链路、模块边界和源码阅读路线图。它适合和 `JayAgent-review学习手册.md` 配套使用。

## 1. 先记住项目主线

这个项目可以先记成一条业务链：

```text
手动审查 / GitHub Webhook / GitLab Webhook
-> 拉取代码 Diff
-> RAG 检索规则
-> Prompt 构造
-> LLM 审查
-> 风险评分
-> 结构化报告
-> 历史存储 / 评论回写 / 企业微信告警
```

如果你先记住这条线，再看每个包就不会散。

## 2. 根包

### `com.jayagent.jayagent_review`

- `JayAgentApplication`：Spring Boot 启动入口，应用从这里启动。

## 3. `agent` 包

这个包是审查引擎的核心，负责把输入变成可解释的审查结果。

- `JayAgentScanner`：核心审查流程编排器，负责规范化输入、调用规则检索、调用模型、交给解析器并生成审查结果。
- `ReviewPromptBuilder`：负责构造检索词、过滤和格式化知识库上下文、生成系统 Prompt。
- `ReviewReportParser`：负责解析模型输出中的摘要、风险项和 PASS 结果，并规范化风险等级与置信度。
- `JayAgentReport`：结构化审查报告对象，承载风险项、评分、摘要和模型分析结果。
- `ScheduledScanner`：定时扫描入口，用于周期性触发审查任务。

### `JayAgentReport` 的内部对象

- `RiskItem`：单条风险项，通常包含级别、标题、描述、建议等信息。

### 这一包你要重点看什么

- 输入如何变成审查上下文
- RAG 如何参与分析
- Prompt 如何拼接
- 模型输出如何解析成结构化对象
- 风险评分如何落到报告上

## 4. `config` 包

这个包负责模型配置、安全控制、评分策略和业务属性映射。

- `AiConfig`：AI 相关配置，通常负责模型客户端或相关 Bean 的装配。
- `ApiKeyAuthFilter`：API Key 鉴权过滤器，拦截请求并校验访问令牌。
- `JayAgentProperties`：`application.yml` 中 `app.jayagent.*` 以及相关业务配置的属性映射类。
- `RiskScoringConfig`：风险评分配置，定义不同风险等级对应的分值或惩罚策略。

### `JayAgentProperties` 的内部对象

- `KnowledgeBase`：知识库相关配置，如自动初始化、源文件路径、状态文件和阈值等。
- `Scoring`：评分相关配置，如 critical/high/medium/low 的惩罚值。
- `Webhook`：Webhook 安全相关配置，如共享密钥、平台 token 和模式开关。
- `Dedup`：Webhook 去重文件、TTL 和过期清理配置。
- `ExternalApi`：外部 API 的超时、重试次数和退避间隔配置。

配置层级要特别注意：知识库、评分、Webhook 和外部 API 位于
`app.jayagent.*` 下；安全配置位于 `app.security.*`；审查历史配置独立位于
`app.review-history.*`，不属于 `JayAgentProperties` 的 `app.jayagent` 前缀。

### 这一包你要重点看什么

- `application.yml` 怎么映射到代码
- API Key 怎么校验
- 风险分数怎么配置
- 知识库和 Webhook 的业务参数在哪里收口

## 5. `controller` 包

这个包负责所有对外 HTTP 接口。

- `ChatController`：聊天或辅助查询接口，通常用于模型交互。
- `JayAgentController`：手动审查入口，用户主动提交审查请求时走这里。
- `ReviewHistoryController`：审查历史查询接口，提供列表、详情和筛选能力。
- `RuleController`：规则库/规则查询接口，供前端或调试查看规则内容。
- `SearchController`：搜索接口，通常用于检索规则、历史或相关审查内容。
- `WebhookController`：Webhook 入口，接收 GitHub/GitLab 等平台推送的变更事件。
- `WebhookEventDedupStore`：Webhook 去重存储接口，用于屏蔽重复事件。
- `FileWebhookEventDedupStore`：基于文件的 Webhook 去重实现。
- `ApiExceptionHandler`：统一处理状态异常、参数校验异常和未预期异常，返回一致的错误结构。
- `SqliteWebhookEventDedupStore`：基于 SQLite 的去重实现，适合多实例共享文件场景。

### `controller.dto`

- `JayAgentScanRequest`：手动审查请求 DTO，封装提交给审查接口的输入参数。

### 这一包你要重点看什么

- 哪些接口是人直接调用的
- 哪些接口是 Webhook 触发的
- 哪些接口是给前端页面或调试工具用的
- 哪些地方做了鉴权、校验和去重

## 6. `service` 包

这个包负责业务编排和数据持久化。

- `WebhookService`：Webhook 审查编排服务，负责把外部事件串成完整审查流程。
- `WebhookReviewOrchestrator`：Webhook 任务转交门面，负责把接收到的事件交给任务承接层。
- `WebhookReviewTaskRepository`：Webhook 任务持久化仓库，负责把任务写入 SQLite 并维护状态。
- `WebhookReviewTaskDispatcher`：后台任务派发器，轮询待处理任务并执行审查。
- `WebhookSecurityService`：集中处理 Webhook 请求限制、签名、Token、共享 Secret 和严格模式。
- `GitHubWebhookParser` / `GitLabWebhookParser`：解析平台原生上下文。
- `DiffAssembler`：组装并限制 Diff，处理分页结果、空 Diff、二进制文件和超长内容。
- `ReviewHistoryService`：审查历史门面，负责对外编排历史保存、查询、统计和迁移接口。
- `ReviewHistoryRepository`：历史持久化仓库。
- `ReviewHistoryMapper`：历史记录映射和 JSON 转换。
- `ReviewHistoryStatisticsService`：历史统计和趋势查询。
- `ReviewHistoryMigrator`：旧 JSONL 迁移器。

### `ReviewHistoryService` 的内部对象

- `ReviewQuery`：历史查询条件对象，承载分页、过滤和检索参数。
- `ReviewRecord`：审查记录实体，表示一条完整历史记录。
- `ReviewContext`：审查上下文，表示一次审查任务在处理时携带的输入信息。

### 这一包你要重点看什么

- 审查流程怎么被编排起来
- Webhook 审查上下文怎么组装
- 历史记录怎么落库
- 查询、筛选、统计是怎么做的

## 7. `integration` 包

这个包负责和外部系统通信。

- `ExternalApiException`：外部 API 调用异常封装，用来统一表达 GitHub/GitLab/其他平台调用失败。
- `ExternalApiCallSupport`：统一执行外部调用，集中处理超时、重试和退避。
- `GitHubApiClient`：GitHub 交互客户端，通常用于拉取 diff、评论回写等。
- `GitLabApiClient`：GitLab 交互客户端，负责类似的拉取和回写能力。
- `WeChatNotifier`：企业微信通知器，用于发送高风险告警消息。

### 这一包你要重点看什么

- 代码变更信息怎么拉取
- 审查评论怎么回写
- 告警消息怎么发送
- 外部 API 异常怎么封装和上抛

## 8. `rag` 包

这个包负责规则库和知识库加载。

- `DocumentLoader`：文档加载器，把规则文件或知识文件读入系统。
- `KnowledgeBaseInitializer`：知识库初始化器，负责启动时加载规则并准备检索数据。

### 这一包你要重点看什么

- 规则文件怎么加载
- 知识库什么时候初始化
- 为什么启动时会有状态文件
- 规则如何进入检索流程

## 9. 模块边界怎么理解

你可以把这个项目理解成一个单体应用里的清晰分层：

- `controller` 负责入口
- `service` 负责编排
- `agent` 负责分析
- `rag` 负责知识
- `integration` 负责平台联动
- `config` 负责配置和安全

这套分层对学习 Spring Boot 很友好，因为它已经不是“几个接口拼起来”的状态，而是能看到较完整的责任边界。

## 10. 项目里几个最重要的职责点

### 10.1 审查引擎

核心类：

- `JayAgentScanner`
- `ReviewPromptBuilder`
- `ReviewReportParser`
- `JayAgentReport`

这组类共同决定“怎么检索规则、怎么调用模型、怎么解析和表达审查结果”。

### 10.2 Webhook 编排

核心类：

- `WebhookController`
- `WebhookService`
- `WebhookEventDedupStore`
- `FileWebhookEventDedupStore`

这组类决定了外部平台事件怎么认证、怎么防重、怎么快速返回 `202 Accepted`，以及如何把任务落到 SQLite 再由后台执行。

### 10.3 历史沉淀

核心类：

- `ReviewHistoryService`
- `ReviewHistoryController`

这组类决定了审查结果怎么查、怎么筛、怎么追踪，以及历史保存如何拆分职责。

### 10.4 平台联动

核心类：

- `GitHubApiClient`
- `GitLabApiClient`
- `WeChatNotifier`
- `ExternalApiCallSupport`

这组类决定了是否能真正和外部平台形成闭环。

## 11. 第九周更新后的职责边界

当前 AI 审查链路为：

```text
JayAgentScanner
  -> ReviewPromptBuilder：检索词、规则上下文和系统 Prompt
  -> VectorStore：检索安全规则
  -> ChatClient：调用 LLM
  -> ReviewReportParser：解析 SUMMARY/RISK/PASS
  -> JayAgentReport：保存结果并计算评分
```

当前 Webhook 链路为：

```text
WebhookController
  -> WebhookSecurityService：鉴权和请求限制
  -> JSON 解析、事件去重
  -> 返回 202 Accepted
  -> WebhookReviewOrchestrator 转交任务
  -> WebhookReviewTaskRepository 持久化任务
  -> WebhookReviewTaskDispatcher 派发任务
  -> GitHub/GitLab API 分页获取变更
  -> DiffAssembler 组装和截断
  -> WebhookService 执行审查
  -> ReviewHistoryService 编排历史接口
  -> ReviewHistoryRepository 写入 SQLite
  -> GitHubApiClient / GitLabApiClient 评论
  -> WeChatNotifier 告警
```

横切能力由 `ApiKeyAuthFilter` 保护非 Webhook API，由 `ApiExceptionHandler` 统一错误响应，由 `ExternalApiCallSupport` 统一外部调用超时和重试，由 `CorrelationIdFilter` 提供请求关联 ID，由 `ObservabilityMetrics` 提供 Prometheus 指标。

Webhook 的具体边界是：`WebhookController` 负责入口接收、JSON 解析和去重；
`WebhookSecurityService` 负责请求体大小、Content-Type、GitHub
HMAC 或 GitLab Token/共享 Secret 校验和事件 ID检查；
`WebhookReviewOrchestrator` 负责任务转交，`WebhookReviewTaskRepository`
负责任务持久化，`WebhookReviewTaskDispatcher` 负责后台派发；
`WebhookService` 负责审查、历史保存、评论回写和告警。Webhook 不是由
`ApiKeyAuthFilter` 进行普通 API Key 鉴权，而是走平台凭证或共享 Webhook Secret。

相关配置使用以下前缀：

```text
app.jayagent.webhook.*
app.jayagent.external-api.*
app.review-history.*
```

## 12. 结合项目评估，你还要特别留意什么

### 安全边界

- Webhook 签名是否足够严格
- 没有有效凭证时是否会误放行
- API Key 的覆盖范围是否清晰

### 结果结构化

- 风险项是否足够稳定
- 结果是否足够适合前端展示和统计
- 模型输出异常时是否有稳妥降级

### 可运维性

- 是否有足够的指标和耗时记录
- 是否容易排查重复事件
- 是否容易看出外部 API 失败原因

### 可扩展性

- 平台适配是否容易扩到更多 Git 平台
- 历史存储是否容易从 SQLite 演进到更正式的数据库
- 去重机制是否容易换成分布式方案

## 13. 一句话总览

这套代码可以理解成：

`controller 接收请求 -> service 编排 -> rag 提供规则 -> agent 做分析 -> integration 负责回写和告警 -> history 负责沉淀`

它已经是一个很适合学习 Spring Boot、Spring AI、RAG、Webhook 安全、第三方集成和结果结构化的完整项目。
