## 第 1 周：稳定性和失败路径

- 解决问题：外部依赖失败时处理方式不统一。

### 任务 1.3 Webhook 去重持久化
- 解决问题：内存幂等不够稳定。
- 为什么重要：防止重复审查和重复告警。
- 建议改哪里：`WebhookController`、持久化层。

## 第 7 周：审查上下文引用增强

### 任务 7.1 审查记录补充平台上下文
- 解决问题：历史记录只能看到结果，不能稳定回指真实代码版本。
- 为什么重要：排查问题时需要知道这次审查对应哪个仓库、哪个 PR/MR、哪个 commit、哪个文件。
- 建议改哪里：`ReviewHistoryService`、`WebhookService`、`WebhookController`。

建议新增字段：

- `platform`
- `repository`
- `branch`
- `commitSha`
- `prNumber`
- `mrIid`
- `sourceUrl`
- `diffHash`

### 任务 7.1.1 审查历史切换 SQLite
- 解决问题：审查历史还停留在 `jsonl` 文件。
- 为什么重要：SQLite 更适合分页、筛选和长期查询。
- 建议改哪里：`ReviewHistoryService`、`application.yml`、`pom.xml`。

建议实现：

- 保留 `ReviewHistoryService` 对外方法不变
- 内部持久化从 `jsonl` 切换到 SQLite
- 启动时自动建表
- 默认数据库文件使用 `data/review-history.db`
- 可选将旧 `jsonl` 数据迁移进 SQLite

### 任务 7.2 GitHub / GitLab Webhook 解析真实引用
- 解决问题：Webhook 审查记录缺少平台原生上下文。
- 为什么重要：历史详情页应该能跳回对应 PR / MR / commit。
- 建议改哪里：`WebhookController`、`GitHubApiClient`、`GitLabApiClient`。

建议实现：

- GitHub 从 payload 中解析 `repository.full_name`、`pull_request.number`、`pull_request.head.sha`、`pull_request.html_url`
- GitLab 从 payload 中解析 `project.path_with_namespace`、`object_attributes.iid`、`object_attributes.last_commit.id`、`object_attributes.url`
- 手动审查保留 `manual` 来源，不强制要求平台字段

### 任务 7.3 前端详情页展示回溯入口
- 解决问题：审查详情页只能看本地记录，不能跳转到代码平台。
- 为什么重要：让审查历史具备更强的追踪和复盘能力。
- 建议改哪里：`index.html`

建议实现：

- 在审查详情中展示平台、仓库、分支、commit、PR/MR 编号
- 如果存在 `sourceUrl`，提供“打开源 PR/MR”入口
- 如果存在 `commitSha`，展示短 hash，便于人工核对

## 8.19 评估后 P0：生产安全边界加固

这一阶段的目标，是先把生产安全边界守住，再继续往稳定性和可维护性推进。核心关注点有三个：

- 未认证请求不能再进入审查链路
- 非 Webhook API 不能再匿名调用
- 敏感原始输出不能默认暴露或落库

### 任务 P0.1 Webhook 严格模式失败关闭

- 解决问题：平台 `secret` 和共享 `secret` 都未配置时，严格模式仍可能放行请求
- 为什么重要：未认证请求可能触发审查、评论和告警，等于把系统入口安全交给不可靠默认值
- 已落实：严格模式缺少任何有效凭证时直接返回 `401`
- 改动位置：`WebhookController`、`application.yml`

### 任务 P0.2 非 Webhook API 统一鉴权

- 解决问题：手动扫描、历史、搜索、聊天测试和规则刷新接口可被匿名调用
- 为什么重要：避免审查数据泄露、模型额度滥用和管理操作被未授权触发
- 已落实：新增 `X-JayAgent-Api-Key` 过滤器，覆盖 `/api/**`，并排除使用平台原生鉴权的 `/api/webhook/**`
- 配置：`JAYAGENT_API_KEY`；开发环境如需显式关闭，设置 `app.security.api-key-enabled=false`
- 改动位置：`ApiKeyAuthFilter`、`application.yml`、`index.html`

### 任务 P0.3 原始模型输出最小化

- 解决问题：原始模型输出可能包含代码、密钥片段或其他敏感上下文
- 为什么重要：降低 API 返回和历史数据库中的敏感信息暴露面
- 已落实：默认不通过 API 暴露，也不写入新的 SQLite 历史记录
- 可控开关：`app.security.expose-raw-analysis`、`app.security.persist-raw-analysis`，默认均为 `false`
- 改动位置：`JayAgentController`、`ReviewHistoryController`、`ReviewHistoryService`、`index.html`

### P0 验收标准

- Webhook 严格模式且未配置任何 `secret` 时返回 `401`
- 非 Webhook API 缺少或携带错误 API Key 时返回 `401`
- 鉴权已启用但服务端未配置 API Key 时返回 `503`，避免错误放行
- 正确 API Key 可以访问手动扫描和历史接口
- 默认响应与新历史记录不包含 `rawAnalysis`
- 主源码编译通过，安全行为测试通过

## 第八周：P0 收口与 P1 稳定性增强

第八周的重点，是把前面的 P0 安全加固真正落到代码、测试和文档上，同时继续推进 P1 稳定性改造，让系统从“可以使用”进一步变成“更稳、更快、更不容易出问题”。

### 任务 8.1 Webhook 异步受理

- 解决问题：Webhook 同步执行 LLM，容易超时并触发平台重复重试
- 目标效果：接收 Webhook 后先返回 `202 Accepted`，审查在后台异步完成
- 改动位置：`WebhookController`、`WebhookService`

### 任务 8.2 外部 API 超时与重试统一

- 解决问题：GitHub、GitLab、企业微信等外部调用的超时和重试策略不统一
- 目标效果：统一使用可配置的连接超时、读取超时、重试次数和回退间隔
- 改动位置：`GitHubApiClient`、`GitLabApiClient`、`WeChatNotifier`、`ExternalApiCallSupport`

### 任务 8.3 Webhook 去重 TTL 化

- 解决问题：文件型去重日志会无限增长，也没有过期清理
- 目标效果：去重记录支持 TTL，到期自动失效并清理
- 改动位置：`FileWebhookEventDedupStore`、`JayAgentProperties`、`application.yml`

### 任务 8.4 知识库初始化失败保护

- 解决问题：知识库初始化失败可能阻断应用启动
- 目标效果：规则库初始化失败时只记录日志，不让整个服务起不来
- 改动位置：`KnowledgeBaseInitializer`

### 任务 8.5 稳定性专项测试

- 解决问题：P1 稳定性改造缺少专门回归测试
- 目标效果：为 `202` 受理、超时重试、TTL 去重、知识库初始化保护补齐测试
- 改动位置：`src/test/java/com/jayagent/jayagent_review/**`

### 第八周验收标准

- Webhook 返回 `202 Accepted`，不再同步等待完整审查结果
- 外部 API 超时和重试行为可配置且可测
- Webhook 去重记录支持 TTL 失效
- 知识库初始化异常不会阻断启动
- 上述能力均有专门测试覆盖

## 第九周：可维护性优化

第九周围绕 8.19 评估中提出的 P2 可维护性问题展开，重点是降低核心类的职责密度、收敛 API 错误处理方式，并补齐接口文档。原则是保持已有接口字段和主要行为兼容，让重构服务于后续学习、测试和迭代。

### 任务 9.1 拆分 `WebhookController` 职责

- 解决问题：控制器同时负责鉴权、请求校验、JSON 解析、去重、平台字段提取、diff 组装、异步提交和外部调用。
- 目标效果：入口层负责请求接收和安全校验，Webhook 数据解析、审查编排和外部平台操作逐步形成清晰边界。
- 当前实施：保留现有构造函数和 `202 Accepted` 行为，先将公共解析和 diff 组装能力抽离为独立组件，降低控制器内部复杂度。
- 改动位置：`WebhookController`、Webhook 解析组件、`WebhookService`

### 任务 9.2 拆分 `JayAgentScanner` 职责

- 解决问题：扫描器同时负责检索词构造、Prompt 拼装、知识库上下文格式化、LLM 调用和模型结果解析。
- 目标效果：扫描器只负责审查主流程，Prompt 构建和报告解析可以独立测试和修改。
- 当前实施：新增 `ReviewPromptBuilder` 和 `ReviewReportParser`。
- 改动位置：`JayAgentScanner`、`ReviewPromptBuilder`、`ReviewReportParser`

### 任务 9.3 收敛 `ReviewHistoryService` 边界

- 解决问题：历史服务同时承担 SQLite 持久化、JSONL 迁移、查询、统计、趋势和领域对象转换。
- 目标效果：保持对外方法稳定，为后续拆分 Repository、Mapper、统计服务和迁移器做好边界准备。
- 当前实施：本周不改变历史接口和 SQLite 行为，先明确职责边界和后续拆分方向。
- 改动位置：`ReviewHistoryService`、`ReviewHistoryController`

### 任务 9.4 统一 API 异常响应

- 解决问题：不同接口的异常响应结构不一致，调用方难以统一处理。
- 目标效果：参数错误、鉴权错误、请求格式错误和服务端异常都返回统一字段。
- 当前实施：新增 `ApiExceptionHandler`，统一输出 `success`、`status`、`message` 和 `timestamp`。
- 改动位置：`ApiExceptionHandler`、各 Controller

### 任务 9.5 补齐 API 文档

- 解决问题：接口参数、返回字段和状态码分散在代码中，学习和联调成本较高。
- 目标效果：形成可供学习、测试和联调使用的接口说明。
- 当前实施：在第九周验收清单中整理主要 API、成功状态和错误状态。
- 改动位置：`note/第九周完成验收清单.md`

### 第九周验收标准

- 扫描 Prompt 构建和报告解析已从 `JayAgentScanner` 中独立出来。
- 统一异常处理能够覆盖状态异常、参数校验异常和未预期异常。
- Webhook 仍然返回 `202 Accepted`，既有安全校验和去重行为不回归。
- 手动扫描和历史接口的既有字段保持兼容。
- 主要 API 的路径、参数、成功状态和错误状态有文档说明。
- 主源码编译通过，已有测试通过。

> 状态说明：第九周的核心目标已经完成。后续阶段继续把 Webhook 入口、外部调用和运行时排障能力做了收口；本节中的“当前实施”和“后续可以继续”属于当周记录，不代表当前代码仍未实现。

## 第四阶段：可观测性和部署能力

本阶段目标是从“有日志”升级到“可以定位问题”，并把 JAR、Docker 和多实例运行边界写清楚。

### 任务 4.1 请求关联和结构化日志

- 已完成：新增 `CorrelationIdFilter`。
- 每个请求生成或透传 `X-Request-Id`，响应回传该值。
- Webhook 后台异步任务继承接收请求的关联 ID。
- `logback-spring.xml` 输出 JSON 日志，包含时间、级别、logger、线程、message、MDC 和异常堆栈。

### 任务 4.2 Micrometer/Prometheus 指标

- 已完成：接入 Spring Boot Actuator 和 Prometheus registry。
- 暴露 `/actuator/health`、`/actuator/info` 和 `/actuator/prometheus`。
- `ObservabilityMetrics` 记录 Webhook 接收、拒绝、重复事件、审查成功/失败、LLM 耗时、RAG 耗时、外部 API 结果和企业微信告警结果。

### 任务 4.3 外部调用和审查失败可区分

- 已完成：`ExternalApiCallSupport` 统一记录 GitHub、GitLab 和企业微信调用成功/失败及耗时。
- 审查失败记录为 `review_failed`，外部 API 失败记录为 `external_api_failure`，企业微信告警失败记录为 `wechat_alert_failed`。
- 认证失败、请求校验失败和重复事件分别通过 Webhook 指标标签区分。

### 任务 4.4 部署边界说明

- 已完成：补充 JAR、Docker、Prometheus 抓取和多实例运行说明。
- 文件型去重适合单实例；多实例需要共享 SQLite 文件和持久化卷。
- 当前异步任务运行在进程内线程池，实例重启可能中断任务；可靠投递仍应演进到消息队列或任务表。

### 第四阶段验收标准

- 可以通过 `X-Request-Id` 追踪一次 Webhook 从接收到后台完成。
- 可以区分认证失败、重复事件、外部 API 失败和模型失败。
- 可以通过 Prometheus 查看审查次数、失败率和关键耗时。
- Docker/JAR/多实例运行边界已写入 [`note/可观测性与部署说明.md`](可观测性与部署说明.md)。

这一阶段围绕当前剩余的三个方向展开：历史服务拆分、可靠投递，以及测试与可观测性收口。目标不是继续堆功能，而是把已有能力拆清楚、补完整、便于长期维护。

### 任务 10.1 拆分 `ReviewHistoryService`

- 解决问题：历史服务同时承担 SQLite 持久化、对象映射、查询、统计和 JSONL 迁移。
- 目标效果：拆成 `Repository`、`Mapper`、统计服务和迁移器，服务层只保留对外编排。
- 先做：梳理现有读写、查询、统计、迁移的调用点。
- 再做：把持久化和对象转换抽出去，保留对外接口不变。
- 验收：历史查询、写入、统计、迁移行为不回归。

### 任务 10.2 为异步任务补可靠投递

- 解决问题：Webhook 后台任务当前依赖进程内线程池，实例重启或异常退出时可能丢任务。
- 目标效果：让任务具备可恢复、可追踪、可重放的承接方式。
- 先做：梳理 Webhook 后台任务的输入、状态、失败路径和重试条件。
- 再做：设计任务持久化或队列承接层，避免只靠内存调度。
- 验收：实例重启后任务不丢失，失败任务可以重新执行或追踪。

### 任务 10.3 补齐集成测试与收口文档

- 解决问题：真实平台联调、接口说明和生产告警规则还不够完整。
- 目标效果：补 Webhook 集成测试、OpenAPI、链路追踪和告警规则。
- 先做：补 GitHub/GitLab Webhook 集成测试，覆盖成功、鉴权失败和重复事件。
- 再做：补 OpenAPI、追踪字段和告警规则说明。
- 验收：Webhook 从接收到完成的链路可定位，接口说明和告警边界可查。
