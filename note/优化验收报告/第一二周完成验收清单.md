# 第一二周完成验收清单

> 这份清单对应项目优化推进计划里的第一、二周目标。写法上我尽量不把它做成“结果摘要”，而是按学习和验收都好用的方式展开：先讲优化前的问题，再讲具体改动，最后讲这些改动解决了什么。

## 一、第一二周的定位

第一二周的重点，不是继续堆功能，而是先把这个 AI 代码审查项目的“基础骨架”立稳。

这一阶段主要做了四件事：

1. 把项目的主链路跑通
2. 把入口和输出统一起来
3. 把知识库和配置收拢到明确的位置
4. 把手动审查、Webhook 和前端展示串成一个可理解的整体

换句话说，第一二周的任务，是让这个项目从“零散代码集合”变成“能讲清楚、能学习、能演示的审查系统”。

## 二、优化前存在的问题

### 2.1 入口不够统一

优化前，项目虽然有不少入口，但它们之间的语义并不完全一致。

主要问题有：

- 手动审查接口和 Webhook 接口的输入字段不完全统一
- 有些地方还在用偏 Demo 风格的参数名
- 不同入口返回的数据结构也不够一致

这会带来一个直接问题：学习者很难一眼看出“一个审查请求从哪里进来、怎么被处理、最后怎么返回”。

### 2.2 结果结构不够清楚

优化前，模型输出和最终返回结果之间还缺少统一的中间结构。

问题主要体现在：

- 结果字段不够稳定
- 风险项、评分、摘要之间的关系没有完全结构化
- 前端展示也只能依赖最基础的数据

这会让后续统计、展示、历史沉淀都比较别扭。

### 2.3 知识库初始化和配置还不够收口

优化前，知识库相关的逻辑虽然已经存在，但从学习角度看还不够“闭环”。

问题包括：

- 规则文件从哪里来、怎么加载、什么时候初始化，这条链路不够显式
- 配置项和运行时行为的对应关系还不够直观
- 学习者很难直接知道哪个配置控制什么行为

### 2.4 前端展示还偏演示型

优化前，前端更像是一个简单的验证页。

它能用，但不够像一个完整项目的一部分。

表现为：

- 展示内容较少
- 和后端输出结构的对应关系不够强
- 很难帮助学习者快速理解审查结果的组成

## 三、第一周主要优化了什么

### 3.1 Webhook 安全边界

#### 优化前的问题

Webhook 是外部入口，如果没有清楚的认证控制，任何人都可能伪造请求触发审查。

优化前的风险点主要是：

- Webhook 入口缺少统一的安全边界说明
- 平台 token 和共享 secret 的关系不够直观
- 严格模式下的失败行为需要更明确

#### 做了什么改动

这一阶段把 Webhook 的安全控制整理清楚了，核心是把不同平台的认证逻辑放到明确的位置。

对应的改动思路包括：

- GitHub Webhook 使用 `X-Hub-Signature-256`
- GitLab Webhook 使用 `X-Gitlab-Token`
- 通用 Webhook 使用 `X-JayAgent-Webhook-Token`
- 严格模式下，缺少有效认证时直接拒绝

#### 作用是什么

这一步的作用，是让 Webhook 不再是“谁都能打进来的入口”，而是变成一个有边界的外部接口。

对学习者来说，它也更容易理解：

- 平台原生认证放在哪里
- 共享认证放在哪里
- 什么情况下会放行，什么情况下会返回 `401`

#### 代码落点

- [WebhookController.java](/F:/JayAgent/JayAgent-review/src/main/java/com/jayagent/jayagent_review/controller/WebhookController.java)
- [application.yml](/F:/JayAgent/JayAgent-review/src/main/resources/application.yml)

### 3.2 Webhook 去重

#### 优化前的问题

Webhook 常常会重复投递。

优化前如果没有去重，可能会出现：

- 同一个事件被重复审查
- 同一条评论被重复回写
- 同一个高风险告警被重复发送

#### 做了什么改动

这一阶段把去重逻辑补了起来：

- 新增去重存储接口
- 新增文件型去重实现
- 按事件 key 记录已经处理过的 Webhook

#### 作用是什么

它解决的是“幂等性”问题。

也就是：即使平台把同一个 Webhook 发了多次，系统也不会重复进入主审查流程。

### 3.3 外部 API 异常封装

#### 优化前的问题

GitHub、GitLab、企业微信这些外部系统一旦失败，之前的错误语义还不够统一。

这会导致：

- 日志里不好看出是哪个平台失败
- 调用失败的来源不够清晰
- 后续不好做统一处理

#### 做了什么改动

新增了统一的外部 API 异常封装，把外部调用失败的上下文收起来。

#### 作用是什么

这样做的好处是：

- 外部平台失败时，日志更容易定位
- 上层业务只需要处理统一的异常语义
- 后续如果要加重试、熔断或告警，也更方便

## 五、第一二周这两轮改动的整体作用

现在你可以比较清楚地看到：

1. 请求怎么进来
2. 知识怎么检索
