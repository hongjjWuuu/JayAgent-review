# JayAgent-review 启动手册

> 这份手册只关心“怎么把项目跑起来”，尽量按最短路径来写。当前项目配置以 `src/main/resources/application.yml` 为准。

## 1. 启动前先确认什么

启动项目之前，先确认下面几项：

- JDK 17
- Maven 3.9+
- 本地 Elasticsearch 可用
- `DEEPSEEK_API_KEY` 已配置
- 如果要走知识库检索，`application.yml` 里的相关配置可以正常加载
- Maven 依赖下载建议走项目内置镜像配置，避免中央仓库超时

## 2. 当前关键配置

以 `src/main/resources/application.yml` 为准，当前最重要的几组配置是：

- `spring.ai.openai.api-key` -> 读取 `DEEPSEEK_API_KEY`
- `spring.ai.openai.base-url` -> `https://api.deepseek.com`
- `spring.elasticsearch.uris` -> 默认 `http://localhost:9200`
- `app.security.api-key-enabled` -> 是否启用 API Key 鉴权
- `app.security.api-key` -> 读取 `JAYAGENT_API_KEY`
- `app.jayagent.knowledge-base.auto-init` -> 是否自动初始化规则库
- `app.jayagent.webhook.*` -> Webhook 认证、请求限制和去重策略
- `app.jayagent.external-api.*` -> GitHub、GitLab、企业微信调用的超时和重试
- `app.review-history.database-file` -> 历史数据库文件

## 3. 最小启动步骤

如果你只是想先跑起来，按这个顺序做：

1. 确认 Docker Desktop 或其他 Elasticsearch 实例正在运行
2. 用纯 URL 检查 Elasticsearch：`Invoke-RestMethod "http://localhost:9200"`
3. 设置 `DEEPSEEK_API_KEY`
4. 设置 `JAYAGENT_API_KEY`，因为当前默认开启普通 API 鉴权
5. 如果 Elasticsearch 不是默认地址，再设置 `SPRING_ELASTICSEARCH_URIS`
6. 执行 `mvn spring-boot:run`
7. 浏览器打开 `http://localhost:8080`

启动后可检查观测端点：

```text
http://localhost:8080/actuator/health
http://localhost:8080/actuator/info
http://localhost:8080/actuator/prometheus
```

每个请求都会返回 `X-Request-Id`。联调 Webhook 时请保留这个值，后台异步审查日志会继续使用同一个关联 ID。生产日志由 `logback-spring.xml` 输出为 JSON。

知识库规则默认使用 `classpath:knowledge/java_security_rules.txt`，因此开发目录、JAR 和 Docker 启动都不需要存在 `src/main/resources` 目录。状态文件 `data/knowledge-base-state.txt` 是外部可写文件，路径相对应用工作目录；可通过 `app.jayagent.knowledge-base.state-file` 改为绝对路径或 `file:` 路径。

不要把 Markdown 链接格式复制到 PowerShell。文档中可以写
`[http://localhost:9200](http://localhost:9200)`，但命令必须写成：

```powershell
Invoke-RestMethod "http://localhost:9200"
```

## 4. 环境变量清单

### 必需项

- `DEEPSEEK_API_KEY`
- `JAYAGENT_API_KEY`：当前 `app.security.api-key-enabled` 默认为 `true`，普通 `/api/**` 接口需要它

### 建议项

- `SPRING_ELASTICSEARCH_URIS`
- `JAYAGENT_API_KEY`
- `JAYAGENT_WEBHOOK_SHARED_SECRET`
- `JAYAGENT_GITHUB_WEBHOOK_SECRET`
- `JAYAGENT_GITLAB_WEBHOOK_TOKEN`

两个 API Key 的用途不同：

| 变量 | 谁使用 | 用途 |
| :--- | :--- | :--- |
| `DEEPSEEK_API_KEY` | JayAgent-review 访问 DeepSeek | 调用 Chat 模型和 Embedding 模型，需使用真实的 DeepSeek 凭证 |
| `JAYAGENT_API_KEY` | 客户端访问 JayAgent-review | 保护普通 API，由本地开发者自行设置 |

示例：

```powershell
$env:DEEPSEEK_API_KEY = "<your-deepseek-api-key>"
$env:JAYAGENT_API_KEY = "<your-local-api-key>"
```

不要把 DeepSeek Key 放到 `X-JayAgent-Api-Key` 请求头，也不要把真实 DeepSeek Key 提交到 Git。

如果启用 Webhook，建议至少配置平台专用凭证：GitHub 使用
`JAYAGENT_GITHUB_WEBHOOK_SECRET`，GitLab 使用
`JAYAGENT_GITLAB_WEBHOOK_TOKEN`。也可以配置
`JAYAGENT_WEBHOOK_SHARED_SECRET` 作为共享 Secret 回退方式。

当前默认 Webhook 策略如下：

- `strict-mode: true`：没有有效凭证时拒绝请求
- `require-event-id: true`：要求平台事件 ID，用于幂等去重
- `max-body-length: 100000`：限制请求体大小
- `allow-shared-secret-fallback: true`：平台凭证缺失时允许共享 Secret 回退
- `dedup.ttl-days: 30`：去重记录保留 30 天
- `dedup-store-type: file`：单机文件去重；可改为 `sqlite` 使用共享 SQLite 文件
- `dedup-store: data/webhook-events.log`：文件去重日志或 SQLite 数据库文件路径

文件实现只适合单实例。多实例必须让所有实例访问同一个 SQLite 文件，并设置：

```yaml
app:
  jayagent:
    webhook:
      dedup-store-type: sqlite
      dedup-store: data/webhook-dedup.db
```

SQLite 使用 `event_key` 主键和 `INSERT OR IGNORE` 抢占事件，重复事件只有一个实例继续处理。不同容器各自使用本地文件时仍然不能实现多实例幂等；生产环境应使用共享存储或后续替换为 Redis/数据库实现。

Webhook 入口为：

```text
POST /api/webhook/github
POST /api/webhook/gitlab
```

GitHub 请求使用 `X-Hub-Signature-256` 校验 HMAC，GitLab 请求使用
`X-Gitlab-Token` 校验 Token。校验和去重通过后立即返回 `202 Accepted`，完整审查在后台执行。

## 5. Elasticsearch 启动方式

项目的 `docker-compose.yml` 提供了 Elasticsearch 8.17.0 单节点服务。首次启动可以执行：

```powershell
docker compose up -d elasticsearch
```

确认容器和端口：

```powershell
docker ps -a --filter "name=es-rag"
Test-NetConnection localhost -Port 9200
```

然后必须用纯 URL 检查 HTTP 响应：

```powershell
Invoke-RestMethod "http://localhost:9200"
```

看到 `name`、`cluster_name`、`version` 和 `tagline` 等信息，才算 Elasticsearch HTTP 服务已经可用。

如果出现以下错误：

```text
Conflict. The container name "/es-rag" is already in use
```

说明容器已经存在，不要重复创建。先查看状态：

```powershell
docker ps -a --filter "name=es-rag"
```

如果状态是 `Exited`，启动已有容器：

```powershell
docker start es-rag
docker logs --tail 100 es-rag
```

如果状态是 `Up` 但请求仍失败，查看日志并等待初始化完成：

```powershell
docker logs --tail 200 es-rag
Invoke-WebRequest "http://localhost:9200" -UseBasicParsing
```

如果 Docker 命令提示无法连接 Docker API，先确认 Docker Desktop 左下角显示 Engine running，再重启 Docker Desktop 或重新打开 PowerShell。

如果已经有现成 ES 实例，就把 `SPRING_ELASTICSEARCH_URIS` 指向它。

本项目 Compose 文件中的两个地址不要混淆：

- Spring Boot 在宿主机运行：使用 `http://localhost:9200`
- Spring Boot 也在 Compose 容器中运行：使用 `http://elasticsearch:9200`

本地执行 `mvn spring-boot:run` 时，使用前者。

Compose 启动时如果提示 `DEEPSEEK_API_KEY`、`GITHUB_TOKEN` 等变量未设置：

- 只执行 `docker compose up -d elasticsearch` 时，这些变量对 Elasticsearch 没有影响
- 如果执行整个 Compose 应用，则需要先设置对应变量
- `version is obsolete` 只是 Compose 新版本提示，不会导致 Elasticsearch 启动失败

## 6. Maven 镜像和编译方式

这次构建使用的是项目内的 Maven 镜像配置文件：

- [maven-settings-aliyun.xml](../maven-settings-aliyun.xml)

它做了两件事：

- 把 `central` 镜像切到阿里云 Maven 镜像
- 加了更偏向长连接和重试的 HTTP 参数，减少下载超时

实际可用的编译命令是：

```powershell
& mvn "-s" "maven-settings-aliyun.xml" "-U" "-Dmaven.repo.local=`${project.basedir}\target\maven-repository" "-DskipTests" "compile"
```

实际可用的测试命令是：

```powershell
& mvn "-s" "maven-settings-aliyun.xml" "-U" "-Dmaven.repo.local=`${project.basedir}\target\maven-repository" "test"
```

建议以后都优先使用这两个命令，原因是：

- 依赖更稳定
- 本地仓库固定在项目目录下，便于复现
- 不依赖全局 `~/.m2` 状态

## 7. JAR 和 Docker 启动验证

打包并确认内置规则已进入 JAR：

```powershell
& .\mvnw.cmd "-s" "maven-settings-aliyun.xml" "-Dmaven.repo.local=`${project.basedir}\target\maven-repository" "package"
jar tf target\*.jar | Select-String "BOOT-INF/classes/knowledge/java_security_rules.txt"
java -jar target\*.jar
```

JAR 启动时规则从 classpath 读取，状态文件和去重文件仍写入当前工作目录下的 `data`。Docker 启动前先完成打包，然后执行：

```powershell
docker compose build jayagent-review
docker compose up -d elasticsearch jayagent-review
docker compose logs -f jayagent-review
```

Compose 中应用容器访问 Elasticsearch 使用 `http://elasticsearch:9200`；宿主机直接运行 JAR 使用 `http://localhost:9200`。如需持久化状态、历史和去重文件，应为应用容器挂载 `data` 目录。

## 8. 启动后先看什么

启动成功后，建议按下面顺序检查：

1. Elasticsearch 请求是否返回集群信息
2. 首页是否能打开
3. 手动审查接口是否能在请求头中带 `X-JayAgent-Api-Key` 后正常调用
4. 规则库是否能正常初始化
5. 历史查询是否能读到数据
6. 如果联调 Webhook，确认请求包含正确的事件 ID、签名或 Token，并检查返回值为 `202`

手动审查接口的最小调用示例：

```powershell
$headers = @{
    "X-JayAgent-Api-Key" = $env:JAYAGENT_API_KEY
    "Content-Type" = "application/json"
}
$body = @{ codeDiff = "class Demo {}" } | ConvertTo-Json

Invoke-RestMethod `
  -Uri "http://localhost:8080/api/jayagent/scan" `
  -Method Post `
  -Headers $headers `
  -Body $body
```

如果返回 `401`，通常是请求头缺失或 API Key 不一致；如果返回 `503`，通常是服务端开启了鉴权但没有设置 `JAYAGENT_API_KEY`。

## 8. 常见启动失败点

- `DEEPSEEK_API_KEY` 没配
- Elasticsearch 没启动
- `SPRING_ELASTICSEARCH_URIS` 指错了
- 本地端口被占用
- `app.security.api-key-enabled` 打开了，但 `JAYAGENT_API_KEY` 没设置
- 把 Markdown 链接 `[http://localhost:9200](http://localhost:9200)` 直接粘贴进 PowerShell
- `es-rag` 容器已存在，重复执行 Compose 导致同名容器冲突
- Elasticsearch 容器仍在初始化，端口已打开但 HTTP 请求暂时被关闭
- Docker Desktop Engine 没有正常运行或当前终端没有 Docker API 权限
- Webhook 严格模式打开了，但平台凭证和共享 Secret 都没设置
- Webhook 请求缺少事件 ID、签名、Token 或使用了非 JSON Content-Type

## 9. 推荐的本地启动顺序

如果想减少排错成本，建议按这个顺序：

1. 先确认 Elasticsearch
2. 再确认 DeepSeek Key
3. 再启动应用
4. 最后验证接口和前端页面

## 10. 一句话记忆

先让 `http://localhost:9200` 返回 Elasticsearch 集群信息，再设置两个不同用途的 Key：
`DEEPSEEK_API_KEY` 给应用访问 DeepSeek，`JAYAGENT_API_KEY` 给客户端访问本项目，最后启动 Spring Boot。

公网 Webhook 的详细方案见 [`Webhook公网访问方案.md`](Webhook公网访问方案.md)。

## 11. 启用 GitHub、GitLab 和企业微信

这几项能力不需要启动额外的 Java 进程。它们都会随 `mvn spring-boot:run` 启动，区别只是需要配置对应的外部平台凭证和回调地址。

完整链路是：

```text
GitHub/GitLab Webhook
 -> WebhookController
 -> 获取 PR/MR Diff
 -> AI 审查
 -> SQLite 历史
 -> GitHub/GitLab 评论
 -> 高风险时企业微信告警
```

### 11.1 外部平台环境变量

在启动应用的同一个 PowerShell 窗口中设置：

```powershell
$env:GITHUB_TOKEN = "你的GitHub访问Token"
$env:GITLAB_TOKEN = "你的GitLab访问Token"
$env:WECHAT_WEBHOOK_KEY = "企业微信机器人Key"
$env:JAYAGENT_GITHUB_WEBHOOK_SECRET = "<your-github-webhook-secret>"
$env:JAYAGENT_GITLAB_WEBHOOK_TOKEN = "<your-gitlab-webhook-token>"
$env:JAYAGENT_WEBHOOK_SHARED_SECRET = "<your-shared-webhook-secret>"
```

这里有两类容易混淆的凭证：

| 凭证                               | 方向           | 用途                         |
| :------------------------------- | :----------- | :------------------------- |
| `GITHUB_TOKEN`                   | 应用 -> GitHub | 获取 PR 文件、回写 PR 评论          |
| `GITLAB_TOKEN`                   | 应用 -> GitLab | 获取 MR 变更、回写 MR 评论          |
| `JAYAGENT_GITHUB_WEBHOOK_SECRET` | GitHub -> 应用 | 验证 GitHub HMAC 签名          |
| `JAYAGENT_GITLAB_WEBHOOK_TOKEN`  | GitLab -> 应用 | 验证 GitLab `X-Gitlab-Token` |
| `JAYAGENT_WEBHOOK_SHARED_SECRET` | 平台 -> 应用     | 平台凭证未配置时的共享 Secret 回退      |
| `WECHAT_WEBHOOK_KEY`             | 应用 -> 企业微信   | 发送高风险 Markdown 告警          |

这些变量只对当前 PowerShell 窗口和随后启动的应用进程有效。设置变量后必须重新启动应用。

### 11.2 GitHub Webhook

#### 创建 GitHub Token

`GITHUB_TOKEN` 需要能够访问目标仓库的 Pull Request，至少应能：

- 读取仓库和 PR 文件 Diff
- 在目标 PR 下创建评论

#### 配置 GitHub 仓库

在 GitHub 仓库中打开：

```text
Settings -> Webhooks -> Add webhook
```

填写：

```text
Payload URL: https://你的公网地址/api/webhook/github
Content type: application/json
Secret: 与 JAYAGENT_GITHUB_WEBHOOK_SECRET 完全一致
事件：Pull requests
```

Webhook 地址必须能从公网访问。`http://localhost:8080/...` 只能被本机访问，GitHub 无法请求本机 localhost。本地联调需要使用公网服务器、反向代理或内网穿透服务提供 HTTPS 地址。

GitHub 请求会携带 `X-Hub-Signature-256` 和 `X-GitHub-Delivery`。应用验证签名和事件 ID 后，返回 `202 Accepted`，再在后台获取 PR Diff、执行审查并回写评论。

### 11.3 GitLab Webhook

#### 创建 GitLab Token

`GITLAB_TOKEN` 需要能够访问目标项目的 Merge Request，至少应能：

- 读取项目和 MR 变更
- 在 MR 下创建评论

当前代码访问的是 GitLab.com API：

```text
https://gitlab.com/api/v4
```

自托管 GitLab 需要先修改 `GitLabApiClient` 的基础地址。

#### 配置 GitLab 项目

在 GitLab 项目中打开：

```text
Settings -> Webhooks
```

填写：

```text
URL: https://你的公网地址/api/webhook/gitlab
Secret token: 与 JAYAGENT_GITLAB_WEBHOOK_TOKEN 完全一致
事件：Merge request events
```

GitLab 请求会携带 `X-Gitlab-Token` 和 `X-Gitlab-Event-UUID`。应用验证 Token 和事件 ID 后返回 `202 Accepted`，后台获取 MR 变更、执行审查并回写评论。

### 11.4 Webhook 的认证和返回结果

Webhook 接口是：

```text
POST /api/webhook/github
POST /api/webhook/gitlab
```

Webhook 不使用普通接口的 `X-JayAgent-Api-Key`，而使用平台签名、平台 Token 或共享 Secret。

默认策略由 `app.jayagent.webhook.*` 控制：

- `strict-mode: true`：没有任何有效认证凭证时返回 `401`
- `require-event-id: true`：没有事件 ID 时返回 `400`
- `max-body-length: 100000`：请求体过大时返回 `413`
- `allow-shared-secret-fallback: true`：允许使用 `X-JayAgent-Webhook-Token` 共享 Secret
- `dedup.ttl-days: 30`：重复事件记录保留 30 天

返回 `202 Accepted` 只表示请求已接受并安排后台处理，不表示 LLM 审查、评论回写或告警已经完成。重复事件也可能返回 `202`，但响应中的 `duplicate` 会是 `true`。

### 11.5 企业微信高风险告警

在企业微信群中打开：

```text
群聊设置 -> 群机器人 -> 添加机器人
```

复制机器人 Webhook URL 中的 `key`，只设置 key 的值：

```powershell
$env:WECHAT_WEBHOOK_KEY = "企业微信机器人Key"
```

当前逻辑只在审查结果包含 `CRITICAL` 或 `HIGH` 风险时发送 Markdown 告警。没有设置该变量时，审查仍会继续，应用只会记录日志并跳过告警。

### 11.6 外部集成功能的启动和联调顺序

建议按阶段验证，不要一开始同时排查所有平台：

1. 先确认 Elasticsearch、DeepSeek 和手动审查正常。
2. 设置 `GITHUB_TOKEN`，确认应用能获取 PR Diff。
3. 配置 GitHub Webhook Secret 和公网 URL，确认回调返回 `202`。
4. 检查 GitHub PR 是否出现 AI 评论，并查询审查历史。
5. 设置 `GITLAB_TOKEN`，再配置 GitLab Webhook 并验证 MR 评论。
6. 最后设置 `WECHAT_WEBHOOK_KEY`，用高风险审查验证企业微信告警。

启动应用后，重点观察：

- Spring Boot 控制台中的 Webhook 接收和后台审查日志
- GitHub PR 或 GitLab MR 评论
- `GET /api/jayagent/history` 返回的历史记录
- 企业微信群中的机器人消息
