# 第四周完成验收清单

> 第四周的主题是“安全和可维护性”。这一周主要是在第一三周打下的基础上，把 Webhook 的安全边界继续收紧，把外部调用的异常语义统一起来，让项目更接近可接入真实团队环境的状态。

## 一、第四周的目标

第四周主要做两类事：

1. 继续加固 Webhook 入口安全
2. 统一外部适配器的异常处理和调用风格

这一周不再是单纯加功能，而是把项目往“可真实使用、可更稳地维护”的方向推进。

## 二、优化前存在的问题

### 2.1 Webhook 入口还可以更严格

优化前，Webhook 已经具备基本校验，但还可以进一步收紧。

主要问题有：

- 请求体大小限制还需要明确
- 事件 ID 校验还不够完整
- strict mode 和共享 token fallback 的关系不够清晰

### 2.2 平台鉴权还可以更标准

优化前，GitHub、GitLab、通用 Webhook 的校验方式虽然已经存在，但还可以更规范地分层。

### 2.3 外部依赖失败策略不够统一

GitHub、GitLab、企业微信这些外部系统如果失败，最好有统一的异常包装和更清晰的日志。

优化前的问题包括：

- 异常抛出方式不统一
- 失败日志语义不够一致
- 后续不好做统一重试或告警

## 三、第四周主要优化了什么

### 3.1 Webhook 安全能力增强

#### 优化前的问题

Webhook 是外部入口，如果请求体、事件 ID、签名校验都不够严格，就容易被伪造事件冲击。

#### 做了什么改动

这一周对 Webhook 做了更细的安全控制：

- 限制请求体大小
- 强制检查事件 ID
- 支持严格模式
- 保留共享 token fallback 作为可控兜底

#### 作用是什么

它让 Webhook 的入口边界更清楚：

- 什么请求能进
- 什么请求会被拒绝
- 什么场景下可以兜底

这对真实接入 GitHub / GitLab 特别重要。

### 3.2 GitHub / GitLab Webhook 原生校验保持

#### 优化前的问题

Webhook 安全不只是“有 token 就行”，更重要的是和平台原生机制对齐。

#### 做了什么改动

- GitHub 使用 `X-Hub-Signature-256`
- GitLab 使用 `X-Gitlab-Token`
- 通用共享 token 作为兜底

#### 作用是什么

这样项目就能更像一个真实的 Webhook 接收服务，而不是简单的 Demo。

#### 代码落点

- [WebhookController.java](/F:/JayAgent/JayAgent-review/src/main/java/com/jayagent/jayagent_review/controller/WebhookController.java)

### 3.3 外部 API 异常统一

#### 优化前的问题

外部 API 失败时，如果异常类型不统一，上层业务就难以区分是哪个平台、哪个动作失败。

#### 做了什么改动

引入统一的外部异常包装：

- GitHub API
- GitLab API
- 企业微信告警

#### 作用是什么

这样日志更容易看懂，后续也更容易做统一处理。

#### 代码落点

- [GitHubApiClient.java](/F:/JayAgent/JayAgent-review/src/main/java/com/jayagent/jayagent_review/integration/GitHubApiClient.java)
- [GitLabApiClient.java](/F:/JayAgent/JayAgent-review/src/main/java/com/jayagent/jayagent_review/integration/GitLabApiClient.java)
- [WeChatNotifier.java](/F:/JayAgent/JayAgent-review/src/main/java/com/jayagent/jayagent_review/integration/WeChatNotifier.java)

### 3.4 外部调用兜底

#### 优化前的问题

GitHub、GitLab 和企业微信如果失败，容易把主审查流程一起影响到。

#### 做了什么改动

把外部调用的失败影响隔离到各自的适配器里，避免一个平台失败拖垮整个审查流程。

#### 作用是什么

这样主流程更稳定，审查结果更容易返回，告警失败也不会直接打断用户体验。
