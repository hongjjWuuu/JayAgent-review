# 第七周完成验收清单
> 第七周的重点，是把审查历史和真实代码上下文真正连起来。前六周已经把审查能力、历史能力、产品化展示和可观测性逐步补齐，这一周进一步解决“这次审查到底对应哪个仓库、哪个分支、哪个 PR/MR、哪个 commit、哪个文件”这个关键问题，让历史记录具备可回溯性和可复盘性。

## 一、本周完成了什么

### 1.1 审查记录补充平台上下文

本周把审查历史从“只有结果”推进到“结果 + 真实来源上下文”。

新增和强化的上下文字段包括：

- `platform`
- `repository`
- `branch`
- `commitSha`
- `prNumber`
- `mrIid`
- `sourceUrl`
- `diffHash`

这些字段让每一条审查记录都不再只是一个抽象结果，而是可以明确对应到某个平台、某个仓库、某次变更和某个具体入口。

### 1.2 审查历史切换到 SQLite

本周把历史存储从 `jsonl` 进一步切换为 SQLite，用数据库的方式承载审查历史。

这一步的目标不是“换一种存储格式”这么简单，而是让历史记录真正具备：

- 分页能力
- 条件筛选能力
- 长期查询能力
- 更稳定的并发读写能力

### 1.3 Webhook 解析真实引用信息

本周补齐了 GitHub / GitLab Webhook 中的真实上下文解析逻辑。

对于不同平台，系统开始能从 payload 中解析出更接近源头的信息，而不是只靠后续补录或人工推断。

### 1.4 前端详情页补充回溯入口

本周还升级了前端详情页，让审查结果不只是“展示出来”，而是可以继续跳回真实代码平台。

这让审查历史的价值从“看得到”变成“查得回去”。

## 二、优化前存在的问题

### 2.1 历史记录只能看到结果，不能稳定回指真实代码版本

优化前，历史记录虽然已经能保存，也能展示部分审查结果，但它和真实代码上下文之间的联系还不够强。

常见问题是：

- 只能知道“审查过了”，不知道对应哪个仓库。
- 能看到审查结论，但不能稳定回跳到 PR / MR 页面。
- 缺少 commit、分支、平台等关键信息时，很难判断这条记录到底对应哪次变更。

对于排障和复盘来说，这种历史记录是不完整的，因为它缺少“回到源头”的能力。

### 2.2 历史数据仍然停留在轻量文件阶段

优化前，审查历史仍然停留在 `jsonl` 文件方案上。这个方案虽然简单，但随着数据增多，会逐渐暴露出明显问题：

- 分页和筛选性能不够稳定。
- 长期查询不够方便。
- 数据结构变化后维护成本高。
- 历史记录越来越多时，后续分析和迁移都不够自然。

也就是说，`jsonl` 适合作为初期方案，但不适合作为长期承载历史查询的基础设施。

### 2.3 Webhook 的平台原生上下文没有被充分利用

优化前，GitHub / GitLab Webhook 虽然已经能触发审查，但 payload 中蕴含的原生上下文没有被完整结构化出来。

结果就是：

- 历史记录和平台页面之间缺少明确链接。
- 审查记录里缺少 commit、分支、PR/MR 编号等关键信息。
- 后续如果想做更精确的回溯，只能依赖额外人工整理。

### 2.4 前端历史详情缺少回到平台的入口

优化前，前端详情页更多是“看本地记录”，而不是“回到真实源头”。

这会让用户在复盘时遇到两个问题：

- 看完历史后，仍然要自己去找平台页面。
- 审查结果和源代码上下文之间的链路不够完整。

这也是第七周必须补的一块内容。

## 三、第七周主要优化了什么

### 3.1 审查历史增加平台上下文字段

第七周最核心的改动之一，是把平台上下文写进历史记录。

#### 做了什么改动

历史数据结构补充了更完整的来源信息，例如：

- 平台类型是 GitHub、GitLab 还是手动审查
- 仓库名是什么
- 分支是什么
- commit SHA 是什么
- PR / MR 编号是什么
- 源链接是什么
- 变更内容的差异哈希是什么

#### 作用是什么

这让历史记录第一次真正有了“可回指性”：

- 看到一条记录，就能知道它来自哪里。
- 后续排查问题时，可以直接跳回对应平台。
- 多次审查同一个仓库时，更容易建立历史对比。

对于一个审查系统来说，这一步非常重要，因为它决定了记录是不是“可用的记录”。

### 3.2 历史持久化从 jsonl 切换到 SQLite

第七周把审查历史从轻量文件存储切换为 SQLite，这是非常关键的一步。

#### 优化前的问题

`jsonl` 的问题不在于不能存，而在于随着数据积累，它不够适合做“查询型历史系统”：

- 分页查询要自己处理更多逻辑。
- 条件筛选没有数据库天然便利。
- 长期增长后文件会越来越难管理。
- 迁移、统计、索引和未来扩展都不够稳。

#### 做了什么改动

历史服务内部持久化方式改为 SQLite，但对外接口保持稳定，不影响上层调用。

同时，启动时支持自动建表，并将数据库文件默认放在：

- `data/review-history.db`

另外也保留了对旧 `jsonl` 数据迁移的可能性，避免历史资产丢失。

#### 作用是什么

这一步让审查历史真正具备了“数据库级管理能力”：

- 查询更自然
- 筛选更灵活
- 维护更稳定
- 后续扩展更容易

对学习者来说，这也是很好的架构示例，因为它展示了如何在不破坏外部 API 的前提下替换内部存储实现。

### 3.3 Webhook 解析真实平台引用

第七周把 GitHub 和 GitLab 的原生 payload 真正用起来了。

#### 做了什么改动

针对不同平台，系统开始从 Webhook payload 中解析这些信息：

GitHub：

- `repository.full_name`
- `pull_request.number`
- `pull_request.head.sha`
- `pull_request.html_url`

GitLab：

- `project.path_with_namespace`
- `object_attributes.iid`
- `object_attributes.last_commit.id`
- `object_attributes.url`

同时，手动审查仍然保留 `manual` 来源，不强制要求平台字段。

#### 作用是什么

这让系统不再只是“收到 Webhook 就审查”，而是能把审查结果和平台真实上下文绑定起来。

它的好处非常直接：

- 历史详情页可以跳回对应 PR / MR。
- 审查记录更容易做跨平台统一管理。
- 以后做趋势分析、仓库维度统计也更容易。

### 3.4 前端详情页增加回溯入口

第七周还把前端详情页补成了更完整的复盘入口。

#### 做了什么改动

详情页开始展示更多平台上下文信息，例如：

- 平台
- 仓库
- 分支
- commit

如果存在 `sourceUrl`，前端还可以提供“打开源 PR/MR”的入口；如果有 `commitSha`，也能展示短 hash 方便人工核对。

#### 作用是什么

这一步让审查结果真正具备“回到现场”的能力。

用户看完历史记录后，不需要再手动复制信息去平台里找，就能顺着详情页继续回到源代码上下文。

## 四、第七周的核心代码内容

### 4.1 `ReviewHistoryService` 的职责进一步扩展

第七周之后，`ReviewHistoryService` 不只是历史保存器，还成了平台上下文管理器。

它负责的事情包括：

- 保存审查结果
- 保存平台上下文
- 查询历史
- 处理分页和筛选
- 提供详情读取
- 支持 SQLite 持久化

### 4.2 `WebhookController` 和平台客户端负责把原始上下文变成结构化数据

这一层的作用是把 Webhook payload 中杂乱的字段整理成统一模型，让后续服务层和前端能够稳定消费。

### 4.3 `index.html` 负责把上下文真正展示出来

页面不再只显示结果，而是开始把“结果从哪里来”也一起展示出来，这对复盘尤其重要。
