# 第八周完成验收清单
> 第八周的重点，是把 8.19 评估后确认的 P0 安全边界真正收口，同时继续把 P1 稳定性改造落到代码和测试上。这个阶段不是再新增更多功能，而是把前面已经具备的能力变得更稳、更安全、更可验证。

## 一、本周完成了什么

### 1.1 生产安全边界加固

第八周先完成了三项 P0 安全收口：

- Webhook 严格模式失败关闭
- 非 Webhook API 统一鉴权
- 原始模型输出最小化

这三项的共同目标，是避免未认证访问、敏感信息暴露和管理接口被匿名调用。

### 1.2 稳定性增强

第八周继续完成了四项 P1 稳定性优化：

- Webhook 异步受理
- 外部 API 超时与重试统一
- Webhook 去重 TTL 化
- 知识库初始化失败保护

这些改造的核心，是减少同步等待、统一外部依赖策略、避免重复请求无限增长，以及避免启动阶段因规则库异常而整体失败。

### 1.3 专门测试补齐

第八周还把这些改造补上了对应测试，确保：

- `202 Accepted` 受理逻辑可验证
- 超时与重试策略可回归
- TTL 去重可过期失效
- 知识库初始化失败不会阻断启动

## 二、优化前存在的问题

### 2.1 Webhook 严格模式仍可能被空凭证放行

优化前，Webhook 严格模式在某些缺少 `secret` 的场景下，仍可能出现请求被放行的风险。

这会带来非常直接的安全问题：

- 未认证请求可能触发审查
- 可能触发评论和告警
- 会让平台默认行为变得不可靠

### 2.2 非 Webhook API 可能被匿名调用

优化前，手动扫描、历史、搜索、聊天测试、规则刷新等接口并没有统一的 API Key 保护。

这意味着：

- 审查数据可能被泄露
- 模型额度可能被滥用
- 管理操作可能被未授权触发

### 2.3 原始模型输出暴露面过大

优化前，原始模型输出存在被 API 暴露或写入历史记录的风险。

原始输出里可能包含：

- 代码片段
- 敏感上下文
- 密钥片段
- 临时分析信息

如果默认暴露，安全边界就会变得很脆弱。

### 2.4 Webhook 仍是同步执行，容易超时

优化前，Webhook 如果同步执行完整 LLM 审查，容易出现：

- 响应过慢
- 平台重试
- 重复审查
- 用户体感卡顿

对于 Webhook 场景来说，同步等待是很容易踩坑的设计。

### 2.5 外部 API 策略不统一

优化前，GitHub、GitLab、企业微信等外部调用的超时和重试策略并不完全统一。

这会让问题排查和后续调优变复杂：

- 有的调用超时快
- 有的调用重试次数不一样
- 有的调用没有统一回退策略

### 2.6 去重日志会持续增长

优化前，文件型 Webhook 去重日志没有很好地控制生命周期。

这会导致：

- 去重记录越来越多
- 文件越来越大
- 没有明确过期清理

### 2.7 知识库初始化失败可能影响启动

优化前，知识库初始化失败如果处理不当，可能会影响应用启动。

这对于服务型项目来说是比较危险的，因为规则库异常不应该直接把整个服务拖垮。

## 三、第八周主要优化了什么

### 3.1 Webhook 严格模式失败关闭

#### 做了什么改动

当 Webhook 严格模式开启，但平台 `secret` 和共享 `secret` 都没有配置时，系统不再放行请求，而是直接返回 `401`。

#### 作用是什么

这一步让“严格模式”真正严格起来，避免认证凭证缺失时发生默认放行。

对于生产环境来说，这是非常关键的边界控制。

#### 代码落点

- [`src/main/java/com/jayagent/jayagent_review/controller/WebhookController.java`](/F:/JayAgent/JayAgent-review/src/main/java/com/jayagent/jayagent_review/controller/WebhookController.java)
- [`src/main/resources/application.yml`](/F:/JayAgent/JayAgent-review/src/main/resources/application.yml)

### 3.2 非 Webhook API 统一鉴权

#### 做了什么改动

新增 `X-JayAgent-Api-Key` 过滤器，对 `/api/**` 统一做 API Key 保护，并排除 `/api/webhook/**` 这种依赖平台原生鉴权的入口。

#### 作用是什么

这让手动扫描、历史查询、搜索、聊天测试、规则刷新等接口都进入统一的安全边界。

如果服务端没有配置 API Key，系统也不会错误放行，而是返回 `503`，避免出现“以为有保护，实际上没保护”的假安全问题。

- [`src/main/resources/application.yml`](/F:/JayAgent/JayAgent-review/src/main/resources/application.yml)
- [`src/main/resources/static/index.html`](/F:/JayAgent/JayAgent-review/src/main/resources/static/index.html)

### 3.3 原始模型输出最小化

#### 做了什么改动

原始模型输出默认不再通过 API 对外暴露，也不再写入新的 SQLite 历史记录。

同时保留了两个可控开关：

- `app.security.expose-raw-analysis`
- `app.security.persist-raw-analysis`

默认值都为 `false`。

#### 作用是什么

这样可以显著降低敏感信息泄露风险。

即使模型内部输出包含代码、路径或其他上下文，也不会在默认情况下扩散到 API 响应和历史库中。

### 3.4 Webhook 异步受理

#### 做了什么改动

Webhook 不再同步等待完整 LLM 审查完成，而是先返回 `202 Accepted`，后台再异步执行审查。

#### 作用是什么

这一步的价值非常明显：

- 降低 Webhook 响应时间
- 减少平台重复重试
- 避免同步链路拖慢入口
- 让审查执行和接收请求解耦

## 四、第八周的核心代码内容

### 4.1 `WebhookController` 和 `WebhookService`

这两个类完成了 Webhook 的“先受理、后审查”改造，也承担了严格模式失败关闭的安全逻辑。

### 4.2 `ApiKeyAuthFilter`

这个过滤器把非 Webhook API 的统一鉴权收口到一处，减少了散落式安全判断。

### 4.3 `ExternalApiCallSupport`

这个支持类把外部调用的超时和重试策略统一起来，是第八周稳定性增强的重要底座。

### 4.4 `FileWebhookEventDedupStore`

这个类负责 Webhook 去重记录的生命周期控制，让重复事件不再无限膨胀。

### 4.5 `KnowledgeBaseInitializer`

这个类把初始化失败保护住，避免规则库异常影响整个应用启动。

## 六、第八周验收结果

第八周完成后，项目可以总结为：

1. 安全边界更清楚了，未认证请求不再容易误入核心链路。
