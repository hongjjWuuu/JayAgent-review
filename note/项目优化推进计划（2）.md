## 二、第一阶段：修复 Webhook 任务可靠性

### 任务 2.1 修复重试次数持久化

- 状态：已完成（2026 年 9 月 10 日）
- 解决问题：`attempt_count` 入队后为 `0`，任务重试时没有更新数据库字段。
- 影响：`WebhookReviewTaskDispatcher.retryOrFail()` 每次读取到的任务次数可能仍然是 `0`，导致失败任务持续重试，不能按预期进入 `FAILED`。
- 修改位置：
  - `src/main/java/com/jayagent/jayagent_review/service/WebhookReviewTaskRepository.java`
  - `src/main/java/com/jayagent/jayagent_review/service/WebhookReviewTaskDispatcher.java`
- 实施方式：
  - 在任务认领或重试更新时递增 `attempt_count`。
  - 让任务状态更新和重试次数更新处于同一次数据库更新中。
  - 明确最大重试次数，避免依赖分散在多个类中的数字常量。
- 验收标准：
  - 第一次失败后 `attempt_count` 变为 `1`。
  - 第二次失败后 `attempt_count` 变为 `2`。
  - 达到最大重试次数后任务进入 `FAILED`。
  - 应用重启后，任务仍能根据数据库中的重试次数继续处理。

### 任务 2.2 增加异步任务重试测试

- 状态：已完成（2026 年 9 月 10 日）
- 解决问题：当前主要测试集中在入口安全和单元逻辑，任务状态流转验证不足。
- 为什么重要：重试逻辑涉及数据库状态，单靠静态检查不能保证正确。
- 修改位置：
  - `src/test/java/com/jayagent/jayagent_review/service/`
  - `WebhookReviewTaskRepository` 相关测试
- 验收标准：
  - 覆盖入队、认领、重试、重新认领和失败终止。
  - 覆盖应用重启后读取任务状态的场景。

## 三、第二阶段：完善 Docker 配置和数据持久化

### 任务 2.3 补充 Docker 环境变量

- 状态：已完成（2026 年 9 月 10 日）
- 解决问题：当前 Compose 只传入 DeepSeek、GitHub API、GitLab API 和企业微信配置，没有传入项目自身的认证配置。
- 修改位置：
  - `docker-compose.yml`
  - `.env.example`（如项目后续新增）
- 需要补充的环境变量：

```text
JAYAGENT_API_KEY
JAYAGENT_GITHUB_WEBHOOK_SECRET
JAYAGENT_GITLAB_WEBHOOK_TOKEN
JAYAGENT_WEBHOOK_SHARED_SECRET
```

- 验收标准：
  - 容器内能够读取 `JAYAGENT_API_KEY`。
  - GitHub Webhook 能使用 HMAC Secret 校验。
  - GitLab Webhook 能使用 Token 校验。
  - 未配置认证信息时，严格模式仍然拒绝未认证请求。

### 任务 2.4 挂载应用数据目录

- 状态：已完成（2026 年 9 月 10 日）
- 解决问题：应用数据库和运行状态文件目前只写在容器内部。
- 主要数据文件：
  - `data/review-history.db`
  - `data/webhook-review-task.db`
  - `data/webhook-events.log`
  - `data/knowledge-base-state.txt`
- 修改位置：
  - `docker-compose.yml`
  - `Dockerfile`
  - `note/启动手册.md`
- 实施方式：

```yaml
volumes:
  - ./data:/app/data
```

- 注意事项：
  - 需要先确认 Dockerfile 中应用工作目录是否为 `/app`。
  - 如果工作目录不同，应将挂载目标调整为实际工作目录下的 `data`。
  - 不要把数据库文件写入镜像层。
- 验收标准：
  - 容器启动后可以在宿主机项目目录的 `data/` 中看到数据库文件。
  - 执行 `docker compose down` 后再次启动，历史记录仍存在。
  - Webhook 去重记录和未完成任务不会因容器重建而丢失。

### 任务 2.5 增加 Docker 健康检查和启动验证

- 状态：健康检查配置已完成；实际容器启停验证待 Docker 引擎恢复（2026 年 9 月 10 日）
- 解决问题：Compose 当前只通过 `depends_on` 控制启动顺序，不能保证 Elasticsearch 已经可以接受请求。
- 修改位置：
  - `docker-compose.yml`
  - `note/启动手册.md`
- 验收标准：
  - Elasticsearch 健康后再启动应用业务验证。
  - 应用能够通过 `/actuator/health` 返回健康状态。
  - 文档明确区分宿主机访问地址 `localhost` 和容器内访问地址 `elasticsearch`。

## 五、第四阶段：恢复完整测试能力

### 任务 2.9 固定 JDK 和 Maven 运行环境

- 解决问题：当前环境没有可用的全局 Maven，Maven Wrapper 创建运行目录时受到权限限制；当前 Java 为 21，而项目目标版本为 17。
- 影响：无法完成可靠的编译和测试验证。
- 建议方案：
  - 优先使用 JDK 17。
  - 配置 Maven 3.9+。
  - 将 Maven 本地仓库放在项目可写目录，例如 `target/maven-repository`。
  - 确认 `mvnw.cmd` 使用的 Maven 下载目录具备写权限。
- 验收标准：

```powershell
mvn -version
java -version
mvn -s maven-settings-aliyun.xml -Dmaven.repo.local=target/maven-repository test
```

  - 编译版本为 Java 17。
  - 完整测试能够执行。
  - 测试失败时能区分代码问题、依赖问题和外部服务问题。

### 任务 2.10 完善关键路径测试

- 重点测试范围：
  - Webhook 任务重试和失败终止。
  - Docker 配置对应的环境变量读取。
  - 数据库文件初始化和重启后恢复。
  - Webhook 去重和任务入队的一致性。
  - Elasticsearch 或 DeepSeek 不可用时的失败行为。
- 验收标准：
  - P0 问题全部有自动化测试覆盖。
  - 测试不依赖真实 GitHub、GitLab 或企业微信服务。
  - 外部联调单独作为集成测试或手动验收步骤。

### 任务 2.12 增强任务状态观测

- 解决问题：当前虽然有任务日志和 Prometheus 指标，但异步任务的重试、失败和积压情况仍需要更清晰的观察入口。
- 修改位置：
  - `WebhookReviewTaskDispatcher.java`
  - `WebhookReviewTaskRepository.java`
  - `ObservabilityMetrics.java`
- 建议增加：
  - 任务入队数量
  - 任务成功数量
  - 任务重试数量
  - 任务失败数量
  - 当前待处理任务数量
  - 任务处理耗时
- 验收标准：
  - 可以通过日志或 `/actuator/prometheus` 判断任务是否积压。
  - 任务失败后能够定位最后一次错误和重试次数。

## 九、推进原则

1. 先修复 P0 问题，再处理文档和体验问题。
2. 每项代码修改必须同步补充对应测试。
3. 每项配置修改必须同步更新启动手册和配置说明。
4. 不把容器内部文件当作长期数据，业务数据必须放在持久化卷中。
5. 不以“接口返回 202”作为任务成功标准，必须继续验证后台任务最终状态。
6. 对真实 GitHub、GitLab 和企业微信联调保持隔离，优先使用可重复的本地测试。
